# GlassIDS: SHAP Explainability Findings 🔍

## 🎯 Objective

I wanted to actually explain what my models are picking up on, not just report their accuracy numbers, especially for the two confusion patterns I already knew were there: Bot getting confused with BENIGN traffic, and the Web Attack subtypes overlapping with each other. SHAP (SHapley Additive exPlanations) assigns each feature a numeric contribution to a given prediction, based on Shapley values from game theory, basically "how much did this specific feature push the prediction away from a baseline expectation." I used it here to look at both global patterns (what matters across many predictions) and one local, single-prediction example.

## 📊 Methodology

- I loaded all three saved models (XGBoost, MLP, CNN) fresh into a new notebook from their serialized files, rather than juggling three separate kernels.
- I used `TreeExplainer` for XGBoost, which computes exact Shapley values efficiently by exploiting the tree structure directly, and `DeepExplainer` for both PyTorch models, which uses a gradient-based approximation instead since there's no tree structure to exploit. `DeepExplainer` also needs a small background reference set (I used 100 samples) to estimate a baseline expectation, `TreeExplainer` doesn't need this.
- Rather than computing SHAP values across the full 504,160-row test set, which would have been a lot of unnecessary compute for what I actually needed, I built a stratified sample: up to 300 rows per class, or every row if a class had fewer than that. This kept the ultra-rare classes (Heartbleed's 2 rows, Infiltration's 7, SQL Injection's 4) fully represented instead of getting lost in a random sample, while keeping the total sample down to about 3,437 rows.
- My SHAP version returns a single 3D array shaped (samples, features, classes) rather than the older list-of-arrays format, worth knowing since this differs across SHAP versions and changes how you index into the output.
- I hit one real bug along the way: my CNN reused a single `nn.ReLU()` instance across three different calls in `forward`, each with a different tensor shape. `DeepExplainer` attaches hooks per module and assumes one module means one position in the computation graph, so reusing the same ReLU object across differently-shaped calls broke its internal bookkeeping. The fix was giving each usage its own separate ReLU instance, which doesn't change the model's actual computation at all (ReLU has no learnable weights), just how it's wired up for the explainer to track.
- For the one local example (a single misclassified flow), I searched the full test set directly for an actual BENIGN flow that XGBoost predicted as Bot, rather than relying on my stratified sample, since that sample wasn't guaranteed to contain one.

## 🔍 Key Findings

1. **No shortcut features anywhere.** Across all three models, the top SHAP drivers for every class I checked were legitimate behavioral flow statistics (window sizes, packet timing, segment sizes), never anything resembling a leaked identifier. This is a good confirmation that my decision to drop Destination Port from the baseline held up even for the classes the models struggle with most.

2. **Bot's false positives come from weak, overlapping evidence, not one broken feature.** In XGBoost's SHAP summary plot for Bot, almost every feature's SHAP values cluster tightly around zero, only `min_seg_size_forward` showed a genuinely clean, well-separated pattern. That tells a specific story: the model doesn't have one strong, reliable signal for Bot, it's aggregating a lot of soft, marginal evidence, and when a BENIGN flow happens to land in the "somewhat Bot-like" range on enough of these weak features at once, the aggregate tips it over the decision boundary. That's a mechanistic explanation for the 397 BENIGN flows misclassified as Bot I'd already found in the baseline's confusion matrix, death by a thousand weak cuts rather than one bad feature.

3. **`Init_Win_bytes_forward` showed an odd, non-monotonic spread I couldn't fully resolve.** Its dependence plot showed SHAP values swinging both strongly positive and strongly negative right around a feature value of zero, with no clean coloring pattern to explain the split. My best guess is that CICFlowMeter sets this feature to 0 or -1 as a sentinel value for flows without a real TCP window (single-packet flows, UDP traffic, truncated connections), meaning "near-zero" is probably a mixed bucket of genuinely bot-like beacon traffic and unrelated flows that just happen to share the same placeholder value. I didn't confirm this properly (would need to slice by protocol or check other sentinel-adjacent fields), so I'm noting it as an open question, not a resolved finding.

4. **XSS and Brute Force lean on nearly identical features, in the same order.** The top four SHAP drivers for both classes were the exact same features (`Init_Win_bytes_backward`, `Fwd IAT Min`, `Flow IAT Min`, `Max Packet Length`), in almost the same rank order. That's much stronger evidence for the "flow-level features can't see HTTP payload content" explanation from the baseline than just asserting it, two attack types that behave completely differently in reality (repeated login attempts vs. a single script-injection payload) are relying on essentially the same evidence to get flagged, because timing and packet-size statistics are the closest available substitute for something the model can't actually observe.

5. **The three models fail on Bot in three visibly different ways, despite near-identical outcomes.** XGBoost's SHAP values stay uniformly weak across almost every feature. The MLP's are mostly weak too, but with a handful of individual points swinging to extreme values (as far as -300), suggesting a decision surface that reacts wildly to a few specific inputs rather than responding smoothly, which fits with the run-to-run training instability I found earlier when retraining it. The CNN's SHAP values are broadly spread across many more features at once, some showing real directional structure, a more genuinely textured attribution pattern than either of the other two. But all three still land on nearly identical, equally bad Bot precision (0.494 for XGBoost, 0.033 for MLP, 0.036 for CNN), so a richer-looking explanation doesn't translate into a better real-world result on its own.

6. **A single local example shows exactly how a false positive happens.** I pulled one actual BENIGN flow that XGBoost misclassified as Bot and generated a waterfall plot for it. The single biggest driver was `min_seg_size_forward`, the same feature that looked like Bot's most reliable global signal, showing up here to steer the model wrong on this specific instance. Three inter-arrival-time features (Flow IAT Max, Bwd IAT Min, Bwd IAT Mean, all in a similar range) added supporting evidence for a "quiet, bursty" connection shape that a Bot beacon would produce but that this particular flow just happened to share while being ordinary traffic. One feature (`Bwd Packets/s`) even pushed in the opposite direction from its usual global pattern on this specific row, reinforcing that the evidence here isn't just weak, it's inconsistent in direction too. The bundled "68 other features" contribution was larger than several of the named individual ones, confirming this false positive is a broad accumulation of small nudges, not one bad feature.

## ⚠️ Limitations

- All of this is based on a stratified sample of 3,437 rows, not the full 504,160-row test set. This should be representative for global patterns, but isn't exhaustive.
- `DeepExplainer`'s attributions for the neural models are a gradient-based approximation relative to a 100-sample background set, not an exact computation the way `TreeExplainer` provides for XGBoost.
- The `Init_Win_bytes_forward` sentinel-value explanation is a hypothesis I didn't confirm, not a verified finding.
- The claim that the MLP has a less stable decision surface than the CNN or XGBoost is based on one class's SHAP plot (Bot), not checked systematically across other classes, worth treating as a reasonable hypothesis this evidence supports rather than something fully proven.
